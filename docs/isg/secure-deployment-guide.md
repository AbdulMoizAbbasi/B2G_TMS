# JazzRadar / B2G TMS — Secure Deployment Guide

This is a pre-deployment checklist. “Current repository state” describes checked-in local configuration, not actual deployed controls. Do not treat completion as proof until an operator provides evidence from the target environment.

| Control | Current repository state | Required pre-deployment action / evidence |
|---|---|---|
| HTTPS and TLS termination | Compose publishes frontend port 80; Nginx listens on 80 and proxies HTTP; no TLS configuration is present. | Terminate TLS at an approved edge; redirect HTTP to HTTPS; verify certificate lifecycle, protocol/cipher policy, and external scans. Document TLS between proxy and backend where trust boundaries require it. |
| Backend port exposure | Compose publishes `8000:8000` in addition to Nginx access. | Remove direct exposure unless required; otherwise allow only trusted proxy/management sources. Provide firewall/security-group and reachability evidence. |
| MariaDB exposure | No host port mapping in Compose; DB joins Compose network. | Keep DB on private network, restrict service-to-service access, verify host firewall and database grants; configure DB TLS if traffic crosses a trust boundary. |
| API docs/OpenAPI | FastAPI defaults expose docs, redoc and schema routes; no auth is attached to framework docs. | Disable or protect docs in production; confirm with an unauthenticated network check after deployment. |
| Secrets | Backend reads environment configuration. JWT key is validated. Sindh scraper Basic credential remains embedded in source. | Rotate/remove source credential and store all secrets in an approved secret manager or protected runtime injection. Use unique per-environment keys and document access, rotation, and incident procedures. Never put secret values in images, source, logs, or documentation. |
| Database least privilege | Compose creates a DB user through variables; actual SQL grants are not verified. | Provide effective grants showing the app account has only required operations and cannot administer MariaDB. Restrict root credentials to controlled administration. |
| Container privileges | Backend Dockerfile does not declare a non-root user. Image tags are not digest-pinned. | Run backend as non-root, minimize capabilities and writable mounts, pin/scanning policy for images, and capture runtime configuration and scan reports. |
| CORS and browser headers | CORS allows `http://localhost:5173`; Nginx config contains no CSP/HSTS/frame/referrer/content-type policy. | Configure explicit trusted UI origins; add and test appropriate security headers at the serving edge; ensure CORS is not used as authentication. |
| TLS to procurement portals | Punjab scraper disables hostname/certificate checks. Sindh scraper has hard-coded Basic credential. One portal uses HTTP. | Restore verified TLS; configure approved CA trust if necessary; rotate/externalize scraper credential. Document any unavoidable HTTP source and compensating controls. |
| Logging and monitoring | Scraper paths use stdout/print diagnostics; repository does not define log retention/alerting. | Centralize logs, redact credentials/tokens/passwords and sensitive URL query values, protect log access, alert on repeated auth failures/admin actions, and establish retention/incident ownership. |
| Backups and recovery | MariaDB named volume and `./data` mount persist data; backup schedule and restore evidence are absent. | Back up DB and mounted checkpoint/retained-file data consistently; encrypt backups; restrict access; test restore and record RPO/RTO approval. |
| Environment segregation | One local Compose stack; no environment profiles or isolation policy evident. | Define dev/test/prod identities, secrets, network/data access and deployment approvals. Do not assume physical host/subnet separation unless authoritative policy requires it. |
| Database migrations | Initial schema dump is mounted for initialization; auth-session SQL migration is manual. | Back up target DB, review migration, apply it once to existing MariaDB before session-enforcing app release, validate indexes/FK and rollback plan. Do not recreate persistent DB volumes to apply schema changes. |
| Security testing and change control | Backend tests exist; no scan workflow, release approval evidence, or annual third-party report is in repository. | Run required unit/integration/security tests, dependency/image scans, code review, and third-party penetration test; track findings to closure and retain change/release records. |

## Deployment architecture proposal (not current implementation)

Use an approved TLS edge to serve the frontend and proxy API traffic only to the backend on a restricted service network. Keep MariaDB private to the backend network. Supply secrets from an approved secret manager. Run non-root, scanned, controlled images. Separate environments logically with distinct credentials and access policies. Add monitoring, backups, and incident response according to JazzWorld standards. Infrastructure architecture and approval must be supplied by the system owner/ISG; this repository does not implement or prove these controls.
